Rezolus is a high-resolution systems performance telemetry agent. One binary runs
in several roles; the first three are long-running services, the rest are on-demand
tools.

MODES:
    agent      (default) Collect system metrics via eBPF/perf and serve them over HTTP.

tool. Run `rezolus <mode> --help` for a mode's options and examples.

=== rezolus recording check --help
--- exit 0
--- stdout
Run every KPI check over a recording and print one line per check
(PASS / WARN / FAIL / INDETERMINATE / ERROR), then a summary line.

THE FILE: checks live on KPIs in a service-extension JSON file, the same
file `recording annotate --queries` embeds for the viewer's KPI dashboard:

    {
      "service_name": "myservice",
      "kpis": [
        {"role": "latency", "title": "p99 request latency",
         "query": "request_latency_seconds", "type": "histogram",
         "check": {"above": 0.25, "quantile": 0.99, "for": "10s"}},
        {"role": "throughput", "title": "Request rate",
         "query": "sum(irate(http_requests_total[10s]))", "type": "delta_counter",
         "check": {"below": 100, "severity": "warn"}}
      ]
    }

`service_name` (required) names the service; `aliases` (a list) and
`service_metadata` (a map) are optional. Each KPI needs `role` (any word;
it groups charts on the dashboard), `title` (keep it unique in the file:
it names the check in output and events), `query` (PromQL) and `type`:
`gauge`, `histogram`, or a counter kind (`delta_counter`, `counter`).
Any other `type` is charted as a counter and evaluated as written.
Optional: `description`, `unit_system`, `subtype`, `percentiles`,
`subgroup`, `subgroup_description`, `full_width`, `denominator`, `check`.
A KPI without `check` is a chart only and is skipped here.

THE CHECK: exactly one of `above` / `below` is the threshold, compared in
the query's own unit (seconds for the histogram above, requests per
second for the rate); the comparison is strict, so a value equal to the
threshold passes. `for` (default 0s) is the shortest run that counts,
written as 500ms, 10s, 1m30s, 2h, 1d, 1.5s, or a bare number of seconds.
`severity` is `fail` (default) or `warn`. A histogram KPI needs `quantile`
in (0, 1]: its query names the raw histogram and the check evaluates
histogram_quantile(<quantile>, <query>) itself, so leave
histogram_quantile out of the query. `quantile` on any other type is an
ERROR. Unknown keys inside `check` are rejected.

WHICH CHECKS RUN: the KPIs embedded in the recording (by
`recording annotate --queries`); else the built-in template whose
`service_name` or `aliases` match the recording's `source` metadata, the
same lookup the viewer makes. --templates <DIR> uses the template JSON
files in DIR instead of the built-in set for that fallback. --queries
<file> runs that file's checks instead of either, and writes nothing.

HOW A CHECK IS EVALUATED: the query runs over the whole recording through
the same engine as `rezolus mcp query`, on a grid of one point per step
(the recording's sampling interval, at most 1s), and must yield exactly
one series (aggregate with sum(...) or add label matchers if it yields
several). A query that matches nothing is an ERROR, not a pass. Each
point is classified: where a value carries an acquisition-window
uncertainty band (rate(), irate(), histogram quantiles) the band is
compared, so `above` fires only when the whole band is above the
threshold and `below` only when it is entirely below; a point whose band
straddles the threshold, or one interpolated across a span the recording
never observed, is INDETERMINATE. A run is consecutive points that do
not pass; a passing point, or a gap of more than 1.5 steps between
points (the engine emits no point where the recording has no data),
ends it. A run violates only if every point in it violates; one
indeterminate point makes the whole run indeterminate, so a long
violation with an intermittent straddle is one long INDETERMINATE window
rather than short violations that never reach `for`. The step is the grid
step or the series' own point spacing, whichever is coarser (a 10 s
sampler on a 1 s grid yields a point per 10 s, each spanning 10 s). A run's
span is (last point - first point + step); it is a window when
span >= for. A check with a violating window is FAIL (WARN for severity
warn) even if it also has indeterminate windows; with only indeterminate
windows it is INDETERMINATE; otherwise PASS.

EXIT STATUS: 2 if any check could not be evaluated (or the command itself
failed), else 1 if any check with severity `fail` failed, else 0. WARN and
INDETERMINATE never fail the run. No checks at all is 0, with a note on
stderr.

MULTI-RECORDING ARCHIVE: with no --recording every recording is checked and
each line is prefixed with its labels; --recording k=v narrows to one. A
recording and its copies (one source copied, or recorded twice from one
agent process) are one recording.

--annotate writes each FAIL/WARN window into the recording as a range
event: kind=check, timestamp=window start, duration_ns=span (the event
ends one step after the last violating point), description=the KPI title,
details=the condition and, on a second line, the check as JSON. The event
id is a hash of the title, the evaluated query, the condition and the
window start: running again rewrites a window that grew and adds nothing
for one that did not, and a window that no longer fires keeps its old
event. The events go into the recording they were evaluated against (each
recording its own when no --recording is given), in its sources' metadata:
in place, or into a copy with -o <new.dendro>. With --json the annotation
report goes to stderr so stdout stays one JSON array.

--json prints an array with one object per check: `recording` (labels),
`title`, `query` (as evaluated), `check`, `status`, `windows` and
`indeterminate` (each with `start` and `end` as RFC 3339, `start_ns`,
`duration_ns`, `points`), and `error` (ERROR only).

EXAMPLES:
    # Run the checks a recording already carries
    rezolus recording check run.dendro

    # Run checks from a file instead (nothing is written to the recording)
    rezolus recording check run.dendro --queries kpis.json

    # CI: fail the job on a violated check, and store the verdicts as events
    rezolus recording check run.dendro --annotate || exit 1

    # One recording of a multi-recording archive, machine-readable
    rezolus recording check fleet.dendro --recording host=web-01 --json

Usage: rezolus recording check [OPTIONS] <FILE>

Arguments:
  <FILE>
          The recording to check (.dendro)

Options:
      --queries <PATH>
          Service-extension JSON whose KPI checks to run, instead of the recording's own

      --recording <KEY=VALUE>
          Which recording of a multi-recording archive to check, as key=value (e.g. --recording source=redis)
          Repeatable: the pairs are ANDed and must together name exactly one
          recording. Without it every recording is checked.

      --annotate
          Write each FAIL/WARN window into the recording as a kind=check range event

  -o, --output <PATH>
          With --annotate, write the events into this new .dendro instead of the recording

      --json
          Print the verdicts as a JSON array instead of one line per check

      --templates <DIR>
          Directory of service-extension template JSON files to use instead of the built-in set, for a recording with no embedded KPIs (matched to the recording's source metadata)

          Print help (see a summary with '-h')

=== rezolus recording combine --help

--- stdout
Assemble two or more .dendro archives into one, a recording per input
recording, which the viewer opens as one combined view. Requires at least
two inputs (one archive with --ab, below) and an output (-o) ending in
.dendro. A recording and its copy (a snapshot, a hindsight dump) given
together are read as one recording, as `rezolus view` reads them.

With `--ab baseline=<input> experiment=<input>` each input's recordings
are labelled arm=baseline or arm=experiment and the viewer opens a
baseline/experiment comparison; an input recording that already carries
the other arm is refused, naming the input. With two inputs, each value
is an input's path or file name. With ONE archive input, each value is
the position of one of its recordings, from 0,
in the order `rezolus mcp describe-recording` lists them.
Every source of a recording, such as a source and its snapshot, takes
its arm. That is the way to compare the two recordings of an archive
combined without --ab, whose labels may be identical.

--pinned, --category and --bypass-time-check applied to the parquet
row-merge and the A/B tarball, which are no longer written; they are
refused.

EXAMPLES:
    # Two hosts recorded separately in one run: one combined view
    rezolus recording combine web-01.dendro web-02.dendro -o run.dendro

    rezolus recording combine a.dendro b.dendro --ab baseline=a.dendro experiment=b.dendro -o ab.dendro

    # Label the two recordings of one archive as an A/B, by position
    rezolus recording combine run.dendro --ab baseline=0 experiment=1 -o ab.dendro

=== rezolus recording convert --help
--- exit 0
--- stdout
Convert a raw recording (concatenated msgpack snapshots, one per sampling
tick, as `rezolus record -o out.raw` wrote them in earlier releases)
into a .dendro archive that the viewer and the rest of
`rezolus recording` can read.

The input may be plain or zstd-compressed; which one it is is detected from
the file's contents, not its name. The output path defaults to the input
with a trailing .zst and then a trailing .raw stripped, and .dendro
appended: rezolus.raw.zst becomes rezolus.dendro, and a name with neither
suffix just gains one (capture.msgpack becomes capture.msgpack.dendro). An
-o that does not end in .dendro is refused.

The archive holds one source labelled source=rezolus (or the value of
--metadata source=...). The sampling interval stamped into its metadata is
inferred from the median gap between snapshot timestamps unless --interval
says otherwise. A recording with fewer than two snapshots falls back to 1s,
so pass --interval if such a recording was made at another cadence.
Inference warns on stderr when the sampled gaps have no dominant cadence, or
when they are closer together than the whole milliseconds the stamped value
can hold; the conversion still succeeds in both cases.

A raw recording carries no systeminfo or metric descriptions: the recorder
fetches those over HTTP from the running rezolus agent while recording (its
/systeminfo and /metrics/descriptions endpoints) and they never enter the
snapshot stream. Without them the conversion still succeeds and every metric
still queries normally; what you lose is the viewer's hardware panel and the
help text beside each metric. Stamp them here if you saved them -- and if
that agent is still running, the same two endpoints can be curled now, at
conversion time, to recover them. They can only be supplied here, which
means reconverting the original raw input over the output (--force).

EXAMPLES:
    # The producing side, with an earlier release, for reference
    rezolus record --url http://AGENT -o rezolus.raw

    # Convert a compressed recording (writes rezolus.dendro)
    rezolus recording convert rezolus.raw.zst

    # Choose the output path
    rezolus recording convert rezolus.raw -o run7.dendro

    # A recording made at a non-default cadence
    rezolus recording convert rezolus.raw --interval 250ms

    # Save the two metadata blobs at record time, from the agent being recorded
    curl -s http://AGENT/systeminfo > sysinfo.json
    curl -s http://AGENT/metrics/descriptions > help.json

    # ...then stamp them into the conversion
    rezolus recording convert rezolus.raw --systeminfo sysinfo.json --descriptions help.json

    # Or pipe one of them straight in, with - for stdin
    curl -s http://AGENT/systeminfo | rezolus recording convert rezolus.raw --systeminfo -

    # Tag the recording the way `rezolus record --metadata` would

=== rezolus recording snapshot --help
--- exit 0
--- stdout
Take a complete, standalone .dendro copy of an archive while
a recorder or `hindsight` is still appending to it.

WHY NOT `cp`: an archive is a SQLite database in WAL mode, so recent
commits live in a `<file>-wal` SIDECAR until they are checkpointed into
the archive. Copying the archive alone leaves them behind, and the copy
reads as a recording that stopped early.

The archive is copied in one read snapshot, its live tail sealed into the
copy, so the copy holds no WAL rows. The writer is never paused and the
original is not modified. The output must end in .dendro and must not
exist.

The result is what to hand to someone else, upload to the static-site
viewer (a browser is given one file and cannot see a sidecar), or keep
as an incident artifact.

EXAMPLES:
    # Grab the last N minutes of a running hindsight buffer
    rezolus recording snapshot /var/lib/rezolus/hindsight.dendro -o incident.dendro

    # ...or of a `rezolus record` still in progress
    rezolus recording snapshot rezolus.dendro -o so-far.dendro

the `rezolus-mcp` skill, which tells the client how to investigate a recording

Registration runs `claude mcp add` when `claude` is on PATH, in the scope given

Claude Code resolves a server name local > project > user. When another scope's
rezolus entry would win over the one written, install says so and names the
command that removes it.
