# Linux hardware sensors with Tegra driver decoding

## Goal

Issue #1203 needs temperatures, power rails, and fan readings beyond GPU NVML.
A Thor inventory supplies concrete device layouts, but one board cannot define
an adapter for every Tegra. This effort uses the single-PR journal lifecycle;
implementation is local and target-hardware acceptance remains open.

## Decision criteria

The code must preserve native identity and units, tolerate missing or broken
sensors, avoid blocking the scrape path, and display every recorded family.
A rollout decision additionally needs measured device-read costs on Thor and
representative Orin boards. Fixture tests and x86 measurements cannot satisfy
that hardware gate.

## Scope and design

The opt-in `sensors` sampler reads standard Linux hwmon and thermal interfaces.
A shared discovery layer caches descriptive metadata and canonical device paths.
Driver decoding handles INA3221 bus voltage/current and derived power, INA238
direct power and bus voltage, and NVIDIA `pwm_tach/rpm`. Board interpretation
is separate: only the observed Thor identity and INA238 device path earn
`scope=system`. Unknown boards retain their native names and labels.

Seven gauge families cover temperature (m°C), power (µW), voltage (mV), current
(mA), fan speed (RPM), PWM command (0–255), and cooling state (driver ordinal).
Their dashboard cards preserve sensor identities and convert presentation units.
No total sums overlapping rails; derived INA3221 power is explicitly labeled.
Orin rail names remain native rather than inheriting Thor's CPU/GPU meanings.

A single blocking worker performs family-major sweeps at a configurable interval
(default 5 seconds), with discovery every 60 seconds when sampling is requested.
Each family has its own acquisition bracket. Failed readings become absent;
an entirely failed family retains its previous acquisition window. Discovery
removal publishes absence as a membership event. Each family has 256 lifetime
slots, never relabeled or reused, so recording segments cannot attach a new
sensor to an old identity. Metadata changes consume a new slot. Exhaustion
warns and skips new identities until restart.

This is a documented exception to mmap-only sampling: these physical readings
come from device interfaces, with no equivalent BPF event stream. Sysfs can
block inside a driver. The worker bounds concurrency, not driver completion
time; a stuck worker prevents additional sweeps and produces a diagnostic.

## Evidence

The supplied `thor-sensors.json` is preserved as a test fixture under
`src/agent/samplers/sensors/linux/fixtures/`. It identifies an AGX Thor Developer
Kit (Tegra264, L4T R39.2.1), five thermal zones, an INA3221, an INA238, and
other hwmon devices. For example, 19744 mV × 240 mA becomes 4738560 µW.
The original inventory missed NVIDIA's nonstandard `rpm`; the updated read-only
`scripts/sensor_inventory.py` captures it, along with available configuration
and overcurrent attributes for off-host interpretation.

An 80-second production-agent run on the local x86 Linux host used only
`sensors`, normal scheduler policy, debug logging, and one JSON scrape per
second. It produced 80 scrapes, 16 device sweeps, and two discovery passes:

| Measurement | Samples | Minimum | Median | Maximum |
| --- | ---: | ---: | ---: | ---: |
| Scrape-path `sensors sampling latency` | 80 | 3 µs | 12 µs | 67 µs |
| Blocking device read sweep | 16 | 20200 µs | 40766 µs | 43124 µs |
| Discovery | 2 | 3103 µs | 4542.5 µs | 5982 µs |

The host exposed 58 identities: 29 temperature, 28 cooling-state, and one fan.
56 values remained readable. One cooling read returned EINVAL and the fan
returned ENODEV; both were absent, the fan's acquisition window remained null,
and each failing family warned once rather than once per scrape. Successful
families advanced at the configured cadence through rediscovery. These are
wall-clock measurements from a debug build, not CPU accounting or worst-case
fleet costs. The only code change after this long run was rejection of PWM
values outside 0–255; this host exposes no PWM channel.

Raw local-run artifacts are `/tmp/rezolus-sensors-local.log`,
`/tmp/rezolus-sensors-local-observations.json`, and
`/tmp/rezolus-sensors-local-snapshot.json`. They are temporary; this table is
the durable measurement record. The validation recipe describes reproduction.

Focused verification passed 13 sensor tests, 8 sampler-attribution tests,
6 configuration tests, one analysis golden test, and all 96 dashboard tests.
The broader binary suite passed **851 tests, with 8 ignored and zero failures**
(`cargo test --locked -p rezolus --bin rezolus -- --test-threads=1`).
The agent built successfully with `cargo build --locked --bin rezolus`. A final
12-second live smoke run on that binary again exposed 58 identities, 56 readable
values, advancing successful windows, and a null window for the failing fan.
The sensor tests cover the Thor fixture and synthetic Orin layouts, control
and fault guards, numeric limits, removal, immutable slots and exhaustion,
window publication/failure, interval throttling, and panic-safe worker ownership.
Synthetic Orin layouts verify decoding contracts, not actual Orin firmware.

## Review and outcome

Discovery review found that cached class aliases could follow a replacement
device and that required thermal/cooling metadata errors were silent. Both
were fixed: cached reads use canonical device paths, metadata errors are
reported with paths, and regression tests cover these cases. The scoped
re-review found both addressed. The independent whole-branch review found no
remaining actionable code issues and accepted the opt-in implementation. It
retained the hardware-deployment gate below; all 20 operational checklist items
and the context of all seven metric families were assessed. An apparent
disabled-group issue was rejected after checking the existing startup pass
that bounds groups without a live sampler to zero members.

Implementation and local validation are available on `tegra-sensors`.
Target-hardware deployment remains **NO-GO pending measurement**: no Thor SSH
access was available, and no Orin inventory or timing run has been supplied.
Opt-in preserves that distinction from fleetwide enablement.

## Deferred or reopen items

- Run the validation recipe on Thor, compare with native sysfs/tegrastats, and
  measure worst-case read and discovery costs before recommending enablement.
- Collect real AGX Orin and NX/Nano inventories before adding board profiles.
- Thresholds, averaging periods, shunt calibration, thermal modes/governors,
  fan-control modes, and overcurrent counters are inventory context, not
  recorded time series in this version. Recordings alone cannot explain them.
- All-family failures preserve the last acquisition window. The live endpoint
  clears readings, but a recorder that deduplicates unchanged windows may
  retain the preceding observation; this feature does not guarantee a recorded
  outage marker. Interpret timestamps and age accordingly.
- No cross-source deduplication with NVML/drive-health or invented NIC identity.
